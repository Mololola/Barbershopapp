# Architecture

Source of truth for product scope: [`product-spec.docx`](./product-spec.docx). This document is the technical architecture derived from that spec.

## Stack

| Layer | Choice | Why |
|---|---|---|
| Mobile | Flutter (Dart), single codebase for iOS + Android | One app for both platforms; strong custom-rendering support for the future 3D haircut designer |
| Backend | Python + FastAPI | Async, typed, and shares a language with the future ML-driven business finance module |
| Data/Auth/Storage/Realtime | Supabase (managed Postgres) | Fast to stand up solo; Postgres underneath stays portable if outgrown |
| Payments (Phase 2) | Stripe Billing + Stripe Connect | Subscription billing with dunning/auto-suspend; payouts for referral rewards |
| Dev tooling | [Graphify](https://github.com/Graphify-Labs/graphify) | Generates a queryable knowledge graph of this repo for AI-assisted development as it grows |

## Client/backend split

Two backends, split by what they're responsible for:

- **Flutter → Supabase directly**: auth (email/password), simple reads (browsing businesses/services/posts), file storage (profile photos, post images/video), realtime subscriptions (live slot availability, chat, feed updates).
- **Flutter → FastAPI service**: anything requiring atomic transactions, money, or server-only secrets — booking creation, review submission → reward calculation, Stripe billing/webhooks, and (Phase 2+) referral-ranking computation and the ML finance module.

Rationale: Supabase's autogenerated APIs are great for CRUD/auth/storage, but business rules (booking races, payment webhooks, reward math) need a real backend process with private secrets and transactional control — hence FastAPI sits in front of Postgres for those paths.

## Business website

Shop owners (and the admin) can also use the product from a computer. The website is the same Flutter app compiled for the web, so it has the same screens, rules and data as the phone; nothing is reimplemented. What differs is presentation and plumbing:

- **Layout by width, not device**: from 900px wide (`lib/core/responsive.dart`) `AdaptiveChrome` (`lib/core/adaptive_chrome.dart`) swaps the bottom tabs for a sidebar, keeps pages at a readable width, and dashboards (home, finance, admin) lay their panels out in columns. Tablets held sideways get the same.
- **Who can use it**: everyone. Customers get the same screens as in the phone app (the product launches as a website first; the store apps follow).
- **Plumbing**: photo/video uploads go through `XFile` (`lib/core/picked_media.dart`) since the browser has no file paths; sign-in links (email confirmation, password reset, Google) return to the website itself; FastAPI allows the website's origin only (`WEB_APP_URL`).
- **Hosting**: a Render static site declared in `render.yaml`, built by `tools/web/build.sh`, with a strict Content-Security-Policy (only this site, Supabase and the API) and no service worker, so a deploy is never masked by a cached old version.

## Admin second factor

Admin access reaches every business and customers' bank details, so it requires a second sign-in factor (an authenticator-app code, Supabase MFA). The database's admin RLS policies (`is_verified_admin()`) and FastAPI's `require_admin` both require the session's `aal2` level; the app sends an admin to `TwoFactorScreen` until they have it.

## Booking concurrency

The spec explicitly calls out "two people book the same slot" as a case that must be *impossible*, not just checked-for. Application-level check-then-insert logic is inherently racy under concurrent requests, so the guarantee lives in the database:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE bookings
  ADD CONSTRAINT no_overlapping_bookings
  EXCLUDE USING gist (
    worker_id WITH =,
    tstzrange(start_time, end_time) WITH &&
  );
```

Two concurrent booking attempts for an overlapping range on the same worker: the database allows exactly one insert to succeed; the second raises an exclusion-violation inside the same transaction. FastAPI catches that and returns `409 Conflict` with a "this slot was just taken" response, prompting the client to re-fetch availability. This holds regardless of app-server race conditions, load balancer routing, or retries.

## Data model (Phase 1 sketch)

Not exhaustive — enough to unblock scaffolding. Extend as Phase 1 features are actually built.

- `profiles` (1:1 with `auth.users`): role (`customer` | `business`), username (unique, case-insensitive — shown on rankings/posts, so collisions would be confusing), avatar
- `businesses`: owner profile, name, locations (address, city, postcode, ISO country), opening hours (optionally split by one break per day; worker schedules likewise), and a `time_zone` derived from the first location — hours are wall-clock times there, and availability/booking checks run in it. Onboarding is two steps: account sign-up (business name, handle, email, password, 18+/authorised attestation — no date of birth), then a post-confirmation wizard (details → ≥1 service → ≥1 staff member) that sets `setup_completed_at`. Customer browse lists only `businesses_public.is_bookable` businesses (an active service and an active staff member exist); by-id lookups ignore it
- `services`: business_id, name, price, duration
- `workers`: business_id, profile_id (nullable — a worker may or may not have their own account), name; a profile can be active (`is_active`) staff at only one business at a time, enforced by a partial unique index. Leaving or removal deactivates the row (history is kept); the DB refuses it while the worker has upcoming confirmed bookings, and refuses inviting someone already on the staff
- `worker_profiles`: 1:1 with `profiles`, opt-in — legal name (first/last/optional second last name, shown to businesses instead of the account username), bio, city, looking-for-work flag. Legal name is self-reported only; no identity verification yet (see Phase 2+)
- `worker_invitations`: business_id, worker_profile_id, status (pending/accepted/declined) — a business invites a worker by username, the worker must accept before `workers.profile_id` gets linked
- `bookings`: worker_id, service_id, customer_id, start_time, end_time, status
- `reviews`: booking_id, shop_rating, worker_rating, haircut_rating, haircut_type, comments
- `posts`, `post_media`, `comments`, `likes`: social feed (Phase 1, basic version only)

Deferred to Phase 2+: `referral_codes` + ranking aggregation tables, `reward_ledger`, `business_finance_inputs` + forecasting output, `haircut_designs` (3D models).

## Roadmap

**Phase 1 (MVP)** — the only phase in active development right now:
- Auth + profile setup (customer / business)
- Business profile + service catalog + opening hours
- Booking engine (with the concurrency guarantee above)
- Reviews (shop / worker / haircut ratings, no reward payout logic yet)
- Basic social feed (text + image posts, likes, comments)

**Phase 2+** (deferred, each is its own design pass before building):
- Ranking/leaderboard system (4 ranking types, weekly/monthly/yearly/all-time)
- Referral code system + reward ledger + Stripe Connect payouts
- Business finance module — built as a free tier (dated monthly/one-off costs, walk-in 'other income', the month's profit and bookings-to-break-even) and Premium at 9.99/month in the shop's currency with a 14-day no-card trial (forecast + break-even day, 12-month history, chair-utilisation heatmap, per-barber and customer-retention stats, priced promotion suggestions, what-if). All figures are computed server-side (`GET /businesses/{id}/finance`, `app/services/finance_analytics.py`), which also enforces the paywall; bookings store `price_cents` at booking time so history stays accurate. Suggestions are rule-based with stated assumptions — an ML model is a later step once there's data to train on
- 3D haircut designer (save/load/share designs, paid extra storage)
- In-app direct messaging
- Unpaid businesses hidden from customers — a shop is listed only while it pays (or is grandfathered). Never subscribed: hidden from creation. Payment failed or subscription ended: still listed for 3 days, then hidden. Hidden shops keep their data and the owner can still sign in; 60 days after the first failed payment (or the end of the subscription; creation if it never subscribed) the business is deleted, and customers keep the review rewards they earned there (`app/jobs/expire_grace_periods.py`). Visibility is computed live by the SQL function `business_hidden_since` (used by `businesses_public`, booking creation, the posts read policy and the deletion job) rather than a stored flag, so it doesn't depend on a scheduled job running on time. Existing bookings stay valid while hidden; new ones are refused
- Cancel any time from the app (Settings › Subscription & billing, linked from the home banner during a trial): `POST /businesses/{id}/subscription/cancel` sets Stripe's `cancel_at_period_end`, so a trial is never charged and a paid month runs out; `/resume` undoes it. The trial end and scheduled cancellation are mirrored into `business_subscriptions` from `customer.subscription.created/updated` webhooks
- Worker identity verification — `worker_profiles` legal name is currently self-reported with no check behind it. Real verification (ID document check, third-party KYC provider, or at minimum a manual admin-review flag) is flagged but intentionally not built yet — it has real compliance/cost implications the spec never scoped, so it needs its own design pass rather than a bolted-on check.
