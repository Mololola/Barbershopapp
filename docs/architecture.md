# Architecture

Source of truth for product scope: [`product-spec.docx`](./product-spec.docx). This document is the technical architecture derived from that spec.

## Stack

| Layer | Choice | Why |
|---|---|---|
| Mobile | Flutter (Dart), single codebase for iOS + Android | One app for both platforms; strong custom-rendering support for the future 3D haircut designer |
| Backend | Python + FastAPI | Async, typed, and shares a language with the future ML-driven business finance module |
| Data/Auth/Storage/Realtime | Supabase (managed Postgres) | Fast to stand up solo; Postgres underneath stays portable if outgrown |
| Payments (Phase 2) | Stripe Billing + Stripe Connect | Subscription billing with dunning/auto-suspend; payouts for referral rewards |
| Dev tooling | [Graphify](https://github.com/Graphify-Labs/graphify) | Generates a queryable knowledge graph of this repo for AI-assisted development as it grows |

## Client/backend split

Two backends, split by what they're responsible for:

- **Flutter → Supabase directly**: auth (email/password), simple reads (browsing businesses/services/posts), file storage (profile photos, post images/video), realtime subscriptions (live slot availability, chat, feed updates).
- **Flutter → FastAPI service**: anything requiring atomic transactions, money, or server-only secrets — booking creation, review submission → reward calculation, Stripe billing/webhooks, and (Phase 2+) referral-ranking computation and the ML finance module.

Rationale: Supabase's autogenerated APIs are great for CRUD/auth/storage, but business rules (booking races, payment webhooks, reward math) need a real backend process with private secrets and transactional control — hence FastAPI sits in front of Postgres for those paths.

## Booking concurrency

The spec explicitly calls out "two people book the same slot" as a case that must be *impossible*, not just checked-for. Application-level check-then-insert logic is inherently racy under concurrent requests, so the guarantee lives in the database:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE bookings
  ADD CONSTRAINT no_overlapping_bookings
  EXCLUDE USING gist (
    worker_id WITH =,
    tstzrange(start_time, end_time) WITH &&
  );
```

Two concurrent booking attempts for an overlapping range on the same worker: the database allows exactly one insert to succeed; the second raises an exclusion-violation inside the same transaction. FastAPI catches that and returns `409 Conflict` with a "this slot was just taken" response, prompting the client to re-fetch availability. This holds regardless of app-server race conditions, load balancer routing, or retries.

## Data model (Phase 1 sketch)

Not exhaustive — enough to unblock scaffolding. Extend as Phase 1 features are actually built.

- `profiles` (1:1 with `auth.users`): role (`customer` | `business`), username (unique, case-insensitive — shown on rankings/posts, so collisions would be confusing), avatar
- `businesses`: owner profile, name, locations, opening hours
- `services`: business_id, name, price, duration
- `workers`: business_id, profile_id (nullable — a worker may or may not have their own account), name
- `bookings`: worker_id, service_id, customer_id, start_time, end_time, status
- `reviews`: booking_id, shop_rating, worker_rating, haircut_rating, haircut_type, comments
- `posts`, `post_media`, `comments`, `likes`: social feed (Phase 1, basic version only)

Deferred to Phase 2+: `referral_codes` + ranking aggregation tables, `reward_ledger`, `business_finance_inputs` + forecasting output, `haircut_designs` (3D models).

## Roadmap

**Phase 1 (MVP)** — the only phase in active development right now:
- Auth + profile setup (customer / business)
- Business profile + service catalog + opening hours
- Booking engine (with the concurrency guarantee above)
- Reviews (shop / worker / haircut ratings, no reward payout logic yet)
- Basic social feed (text + image posts, likes, comments)

**Phase 2+** (deferred, each is its own design pass before building):
- Ranking/leaderboard system (4 ranking types, weekly/monthly/yearly/all-time)
- Referral code system + reward ledger + Stripe Connect payouts
- Business finance module (monthly cost input → break-even recommendations; ML-driven)
- 3D haircut designer (save/load/share designs, paid extra storage)
- In-app direct messaging
- Auto-suspend/resume business accounts on failed subscription payment
